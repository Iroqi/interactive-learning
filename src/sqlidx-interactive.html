1为什么慢：全表扫描

没有索引时，查询只能全表扫描（type=ALL）：从第一行读到最后一行的数据页，逐行判断 WHERE。百万行表一次扫描要读几十万个数据页，这就是慢查询的第一来源。

EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- type: ALL   rows: 1_000_000   # 全表扫 100 万行 → 慢

练习：慢查询定位

2索引的底层：B+ 树

InnoDB 用 B+ 树：非叶子节点存键值+指针（扇出高，几层就能覆盖百万行），叶子节点存有序的数据行/主键并按链表相连。查找从根往下二分，复杂度 O(log n)，百万行只需 3~4 次磁盘 IO。

为什么 B+ 树快：高度矮（层数≈3）、叶子有序（范围查询走链表）、扇出大（一个节点装几百个键）。

练习：B+ 树特性

3EXPLAIN 判读器：type / key / rows

EXPLAIN 输出最关键三列：type（访问方式，从差到好：ALL → index → range → ref → eq_ref → const）、key（实际用到的索引名）、rows（预估扫描行数，越小越好）、Extra（如 Using index / Using filesort）。

4单列索引：一个条件的加速

CREATE INDEX idx_user ON orders(user_id) 后，WHERE user_id = 42 走索引（type=ref），只扫命中的行。索引是空间换时间：额外占用磁盘，写入（INSERT/UPDATE）要同步维护索引。

练习：索引收益判断

5复合索引：最左前缀

复合索引 (a, b, c) 按 a→b→c 排序。只有从最左列开始连续匹配的条件才能用上索引：WHERE a=1 ✓、WHERE a=1 AND b=2 ✓、WHERE b=2 ✗（跳过了 a）、WHERE a=1 AND c=3 部分用（只用到 a）。

设计原则：把区分度高的列放左边；把等值查询列放前面，范围查询（>、BETWEEN）放后面。

练习：最左前缀判断

6覆盖索引：不回表

二级索引的叶子只存"索引列 + 主键"。如果 SELECT 的列全部在索引里（Extra 显示 Using index），就不需要回表取整行，少一次 IO。反之 SELECT * 通常要回表。

CREATE INDEX idx_uid_status ON orders(user_id, status);
SELECT user_id, status FROM orders WHERE user_id = 42;
-- Extra: Using index   # 覆盖索引，不回表 → 更快

练习：覆盖索引判断

7索引失效：常见坑

以下写法会让索引失效：① LIKE '%xxx'（前导通配符）；② 对列做函数运算 WHERE YEAR(created)=2026；③ 隐式类型转换 WHERE phone=13800000000（phone 是字符串）；④ WHERE name IS NULL 走不了普通索引（可用 IS NULL 索引优化）。

练习：失效场景辨识

8回表与主键选择

InnoDB 聚簇索引（主键）的叶子就是整行数据；二级索引叶子存主键值。查二级索引 → 再按主键回表取行 = 回表。主键建议用自增/紧凑值：B+ 树插入有序、页分裂少；UUID 随机主键会让叶子频繁分裂。

练习：回表判断
