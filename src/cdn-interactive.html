1CDN 是什么 · 回源

CDN（Content Delivery Network）把源站内容缓存到离用户最近的边缘节点。用户请求先打到边缘，命中就直接返回（HIT）；未命中则回源（cache miss → origin fetch），拿到响应后缓存再返回。回源成本远高于命中，所以缓存命中率是 CDN 的核心指标。

用户 → 边缘节点 (POP)
         ├─ HIT  → 直接返回缓存内容 (ms 级)
         └─ MISS → 回源站 origin → 缓存 → 返回

2缓存命中与 TTL

边缘节点缓存对象时记录 TTL（Time To Live，单位秒）。TTL 内请求直接 HIT；TTL 过期后节点要么回源重新拉取，要么发起条件请求（If-None-Match / If-Modified-Since）做协商缓存。TTL 由源站响应头决定，CDN 可覆盖但不应随意缩短。

HTTP/1.1 200 OK
Cache-Control: max-age=3600    ← 边缘缓存 3600 秒
Age: 120                       ← 已在缓存中存活 120 秒
X-Cache: HIT                   ← 边缘命中

3Cache-Control · 边缘 vs 浏览器

Cache-Control 是缓存行为的核心指令。max-age=N 指定缓存秒数；s-maxage=N 仅对共享缓存（CDN/代理）生效，优先级高于 max-age；no-store 禁止任何缓存；private 只允许浏览器缓存、CDN 不缓存；public 允许所有缓存；no-cache 可缓存但每次必须协商验证。

Cache-Control: public, s-maxage=86400, max-age=3600
  → CDN 缓存 24h，浏览器缓存 1h

Cache-Control: private, max-age=600
  → CDN 不缓存，浏览器缓存 10 分钟

Cache-Control: no-store
  → 任何缓存都不存（含 CDN 与浏览器）

  • 理解 private / no-store / no-cache

练习：Cache-Control

4缓存键与 Vary

边缘缓存的键（cache key）默认是 scheme + host + path + query。同一 URL 返回不同内容（如按 Accept-Encoding 返回 gzip / brotli，或按 User-Agent 返回不同页面）时，必须让源站响应 Vary 头告诉 CDN 按哪些请求头分片缓存。缺少 Vary 会导致一种变体覆盖另一种。

Vary: Accept-Encoding, Cookie
  → 缓存键 = URL + Accept-Encoding + Cookie
  → gzip 与 br 各存一份；带 Cookie 与不带各存一份

Vary: *
  → 永远不缓存（每个请求都回源）
本节任务
  • 理解缓存键的组成
  • 知道 Vary 的作用与风险

练习：Vary

5ETag / Last-Modified 条件请求

TTL 过期后，边缘不一定要回源拉完整内容。源站若返回过 ETag（内容指纹）或 Last-Modified（最后修改时间），边缘会发条件请求：If-None-Match 带 ETag、If-Modified-Since 带时间。源站比对后若未变化返回 304 Not Modified（无 body，极小开销）；变化了返回 200 + 新内容。

GET /style.css HTTP/1.1
If-None-Match: "abc123"
If-Modified-Since: Wed, 01 Oct 2026 00:00:00 GMT

← 304 Not Modified          ← 内容未变，无 body
← 200 OK + 新内容            ← 内容已变
本节任务

  • 区分 ETag 与 Last-Modified

练习：条件请求

6缓存失效 · purge 与版本化

内容更新后必须让边缘旧缓存失效。两种方式：purge（主动通知 CDN 删除指定 URL 的缓存）与版本化（文件名带 hash，如 app.a3f2c1.js，天然绕过缓存）。purge 有传播延迟（CDN 数百节点同步需秒级到分钟级）；版本化无延迟但需要构建工具支持。

# purge 指定 URL
curl -X PURGE https://cdn.example.com/index.html

# 版本化：文件名含内容 hash
<script src="/js/app.a3f2c1.js"></script>
  → 内容变 → hash 变 → URL 变 → 天然 MISS 拿新版
本节任务
  • 理解 purge 的传播延迟
  • 知道版本化是更可靠的失效方式

7回源防护 · 击穿 / 穿透 / 雪崩

三大回源故障：缓存击穿——热点 key 过期瞬间大量并发回源（解决：单飞锁 singleflight / stale-while-revalidate）；缓存穿透——请求的 key 永远不在缓存（如恶意随机 URL，解决：布隆过滤 / 空值短缓存）；缓存雪崩——大批 key 同时过期（解决：TTL 加随机抖动 jitter）。stale-while-revalidate 让边缘先返回过期缓存、后台异步回源刷新，是防击穿利器。

Cache-Control: max-age=3600, stale-while-revalidate=60
  → 3600s 内正常 HIT
  → 过期后 60s 内先返回旧缓存，后台异步回源刷新
  → 超过 60s 才同步回源

TTL jitter: base=3600 + random(0, 300)
  → 避免大批 key 同时过期 → 防雪崩
本节任务

8静态资源版本化与部署策略

生产部署最佳实践：HTML 用 no-cache（每次都协商，保证拿到最新入口）；JS/CSS/图片用内容 hash 文件名 + max-age=31536000（一年强缓存，hash 变即新版本）。部署时新旧文件并存（旧 hash 文件不删），避免用户在旧页面点击时 404。CDN 配置 immutable 可让浏览器跳过条件请求。

<!-- HTML: 不缓存，每次协商 -->
Cache-Control: no-cache

<!-- JS/CSS: 内容 hash + 长缓存 -->
Cache-Control: public, max-age=31536000, immutable

部署：新旧 hash 文件并存 ≥ 24h，再清理旧版
